# Embed Syncthing, arm the whitelist, verify off-device

Build Syncbox as a single-activity Kotlin/Compose app that runs unmodified upstream Syncthing in-process through a thin gomobile bridge, controls it over the localhost REST API, implements selective sync as an app-owned `.stignore` whitelist ending in `*` on a receive-only folder, and runs each manual sync as one user-initiated data transfer (UIDT) job with no foreground service and no wake lock. The research confirms almost every existing decision and proposal: three shipping apps use the same embedding, one of them (Sushitrain/Synctrain) ships the same whitelist mechanism on unpatched Syncthing, and Android's own guidance names UIDT as the tool for a user-started transfer. One real conflict was found: stock Syncthing has no "receive the index but hold downloads" switch, so anything left whitelisted is pulled about a second after the index arrives, which contradicts "nothing downloads until Sync is pressed" and the sync-network setting. Four things should change: selection intent must live in the app, separate from the ignore file; the app needs its own cached file tree; backup rules must exclude synced data and the Syncthing identity; and the "no prototypes yet" rule should admit an early engine test harness, because the design cannot be frozen without it. Nothing in the underlying notes was built or run, so the report separates what was read in a primary source from what is inferred and what is assumed. The highest-leverage finding for agent-driven development is that most open questions are Syncthing behaviours that can be settled by host-side Go tests on `linux/amd64`, with no emulator.

Evidence labels used throughout: **[V]** means read in a cited primary source (documentation or source code) on 2026-11-14, not executed; **[I]** means an inference from reading how code paths combine; **[U]** means an untested assumption or unsourced background knowledge. Most Syncthing source was read on `main`, not on the `v2.1.7` tag the project proposes, so every [V] source-level fact needs a re-check at the pinned commit.

## In-process Syncthing is the standard; frequent restarts are untrodden

**The proposed integration is confirmed.** Of the four approaches that exist, the in-process Go library is the one every newer app uses: BasicSync on Android ("Runs Syncthing as a library in the main process"), SyncUp on Android and iOS, and Sushitrain on iOS/macOS [V] ([BasicSync README](https://raw.githubusercontent.com/chenxiaolong/BasicSync/master/README.md), [SyncUp](https://github.com/siddarthkay/syncup), [Sushitrain](https://github.com/pixelspark/sushitrain)). The alternatives are weaker for this product. The official Android wrapper was archived in December 2024, and its surviving fork ships Syncthing as an exec'ed binary that needs extracted native libraries and is exposed to Android 12+ child-process limits, which is the reason BasicSync gives for avoiding that model [V] ([syncthing-android](https://github.com/syncthing/syncthing-android), [BasicSync README](https://raw.githubusercontent.com/chenxiaolong/BasicSync/master/README.md)). The only JVM protocol client on Android last shipped a re-release "with no code changes" [V] ([F-Droid: Syncthing-Lite](https://f-droid.org/en/packages/com.github.catfriend1.syncthinglite/)). SyncUp already uses exactly the split Syncbox proposes: gomobile for lifecycle, REST on `127.0.0.1` for everything else [V] ([SyncUp](https://github.com/siddarthkay/syncup)).

**The embedding API is small and explicitly unstable.** `lib/syncthing` exposes `New(cfg, sdb, evLogger, cert, opts)`, `Start`, `Stop`, `Wait`, and helpers for the certificate, config and SQLite database; `Internals` adds 21 methods such as `GlobalTree`, `SetIgnores`, `NeedSize` and `DownloadBlock`, with the comment that it is "not intended as a stable API at this time" [V] ([syncthing.go](https://raw.githubusercontent.com/syncthing/syncthing/main/lib/syncthing/syncthing.go), [internals.go](https://raw.githubusercontent.com/syncthing/syncthing/main/lib/syncthing/internals.go)). The Go module path still has no `/v2`, so **v2 tags cannot be imported and embedders pin a commit pseudo-version**; Sushitrain does this and copies Syncthing's two `replace` directives, which a consuming module does not inherit [V] ([forum 25532](https://forum.syncthing.net/t/go-module-path-for-syncthing-lib-remains-at-v1-unable-to-import-v2/25532), [SushitrainCore/go.mod](https://raw.githubusercontent.com/pixelspark/sushitrain/main/SushitrainCore/go.mod)). REST is the surface Syncthing versions for compatibility, which is why the recommendation is a bridge of about five functions (start with config, stop, state callback, API address, API key and certificate) with no Syncthing type crossing the boundary, and all data over REST plus `/rest/events` long-polling [I]. gobind cannot pass slices, maps or structs by value, and a panic crossing the boundary exits the program, which reinforces keeping the bridge thin [V] ([gobind docs](https://pkg.go.dev/golang.org/x/mobile/cmd/gobind)). If `/rest/db/browse` proves too heavy for a 100k-file tree, add one bridge function that returns JSON bytes from `Internals`; do not move the whole control surface to Go calls [I].

Two REST details matter for the design. The API service and the folder summary service start only when the GUI is enabled, so the GUI must stay on even though the app never shows it; Sushitrain turns it off only because it uses `Internals` instead [V] ([syncthing.go](https://raw.githubusercontent.com/syncthing/syncthing/main/lib/syncthing/syncthing.go)). And loopback TCP is reachable by every app in the same Android user, so the random API key is the protection; BasicSync forces HTTPS with a certificate handed through the bridge rather than adding a cleartext exception [V] ([stbridge.go](https://raw.githubusercontent.com/chenxiaolong/BasicSync/master/stbridge/stbridge.go)). A UNIX-socket GUI address in app-private storage would remove the port and the exposure, since Syncthing's config accepts one [V] ([config docs](https://docs.syncthing.net/users/config.html)), but no Android app was found doing it [U].

**Start-stop-start in one process is the least proven part of the plan.** Syncbox starts Syncthing whenever the app is visible and stops it when the app leaves or a sync ends. BasicSync's bridge builds a fresh context, config wrapper, database handle and `App` on each run, serialized by a mutex, so repeated restart is exercised in production [V] ([stbridge.go](https://raw.githubusercontent.com/chenxiaolong/BasicSync/master/stbridge/stbridge.go)). Sushitrain, by contrast, refuses a second `Load` on the same client [V] ([sushitrain.go](https://raw.githubusercontent.com/pixelspark/sushitrain/main/SushitrainCore/src/sushitrain.go)). Syncthing also touches process-global state (the `locations` table, `SQLITE_TMPDIR`, file-descriptor limits) [V] ([db_open.go](https://raw.githubusercontent.com/syncthing/syncthing/main/internal/db/sqlite/db_open.go)). No source documents leak-free restart, startup time, shutdown time or memory use on Android [U]. Whether `App.Stop` closes the database or the caller must is unverified; getting it wrong either leaves the WAL unchecked or locks the next open [U]. The safeguard is a stop timeout plus a fallback: kill the app's own process when no UI is visible, or host the engine in a dedicated `android:process`, which restores the clean-slate property of the subprocess model without exec'ing a binary [I].

**The Go runtime as a shared library is the standing platform risk.** Go's SIGSYS safety net does not register when Go is loaded as a shared library, so a newly probed syscall blocked by app seccomp kills the app; a BasicSync crash on a 16 KB x86-64 emulator from a blocked `epoll_wait` was fixed in Syncthing only by a dependency bump [V] ([pidfdhack](https://raw.githubusercontent.com/chenxiaolong/BasicSync/master/stbridge/pidfdhack/pidfdhack_android.go), [Syncthing PR 10783](https://github.com/syncthing/syncthing/pull/10783)). Apps cannot bind netlink route sockets since Android 11, which Syncthing works around with `anet`; that library forces `-checklinkname=0` on the whole binary [V] ([golang/go#40569](https://golang.org/issue/40569), [anet](https://github.com/wlynxg/anet)). The consequence is a rule: **every Go, NDK or Syncthing bump is a runtime test inside the installed app, never through `adb shell`**, which the project's existing 16 KB proposal already says [I]. A Go panic kills the whole app with a poor trace, so the bridge should redirect Go stderr to a file from its first line [I].

Configuration forced on every start follows the two reference apps: no upgrades, usage reporting off (`urAccepted = -1`), crash reporting off (it defaults to on and sends reports to Syncthing's servers), no browser [V] ([stbridge.go](https://raw.githubusercontent.com/chenxiaolong/BasicSync/master/stbridge/stbridge.go), [config docs](https://docs.syncthing.net/users/config.html)). Because Syncbox never runs long enough for a periodic maintenance timer, the bridge should trigger `StartMaintenance()` at the end of a completed sync; what maintenance costs is unmeasured [I]. Licensing is unproblematic: Syncthing is MPL-2.0, Syncbox can carry any licence as long as the exact Syncthing commit is named and any patched file is published, and BasicSync's GPL-3.0 code must be read, not copied [I]. No official Syncthing trademark policy page was found; prior art uses its own name and icon plus a non-endorsement line [V] ([Sushitrain](https://github.com/pixelspark/sushitrain)).

## The whitelist is proven; the Sync button is what Syncthing lacks

**The mechanism is correct as proposed.** Sushitrain writes a strictly validated `.stignore` of `!/path` lines followed by `*`, on unpatched upstream Syncthing; the global index still syncs and the client simply does not pull ignored files [V] ([Sushitrain README](https://github.com/pixelspark/sushitrain/blob/1ed5e2c4728cca8f1673dfb2ae241affa58e7b53/README.md)). Parents need no un-ignoring because the puller recreates missing parent directories, and a line without a trailing slash is compiled as both `line` and `line/**`, so `!/Movies` covers current and future children, which is exactly flow 3's "including files added to it later" [V] ([ignore.go](https://github.com/syncthing/syncthing/blob/ed2e0fd441cf4ed797f6dee6e3db4d1a6ddb82f5/lib/ignore/ignore.go#L528), [folder_sendrecv.go](https://github.com/syncthing/syncthing/blob/ed2e0fd441cf4ed797f6dee6e3db4d1a6ddb82f5/lib/model/folder_sendrecv.go#L681)). `/rest/db/browse` returns the global tree including locally ignored files with name, type, size and modification time [V] ([db/browse](https://docs.syncthing.net/rest/db-browse-get.html)).

**Receive-only is the right folder type, and deselecting is safe in one order.** A receive-only folder clears the version on local changes so they can never become the globally best version; even a mis-ordered local delete cannot reach the computer [V] ([folder_recvonly.go](https://github.com/syncthing/syncthing/blob/ed2e0fd441cf4ed797f6dee6e3db4d1a6ddb82f5/lib/model/folder_recvonly.go#L28), [indexhandler.go](https://github.com/syncthing/syncthing/blob/ed2e0fd441cf4ed797f6dee6e3db4d1a6ddb82f5/lib/model/indexhandler.go#L480)). Sushitrain rewrites ignores first and only then deletes the local copy [V] ([folder.go](https://github.com/pixelspark/sushitrain/blob/1ed5e2c4728cca8f1673dfb2ae241affa58e7b53/SushitrainCore/src/folder.go#L1304)). Because every scan reloads `.stignore` before looking at files, the row becomes "ignored" rather than "deleted", nothing shows as a local change, and the computer counts the phone as in sync for that file [I]. The reverse order records a "deleted, receive-only changed" row that heals only while Syncthing keeps running, and Syncbox stops Syncthing quickly, so the app must enforce the order: write ignores, wait for the scheduled scan to finish, then delete the file, its `.syncthing.<name>.tmp` and empty parents [I]. With Syncthing stopped (offline mode), writing `.stignore` directly and deleting is equally safe because the next start loads ignores before its first scan [I]. Selecting a file that is not yet on disk transiently produces a receive-only "deleted" row until it is pulled, so **the app must not treat `receiveOnlyChanged*` counters as errors and must never call `/rest/db/revert` as cleanup** [I]. Older forum reports of receive-only folders stuck with spurious local additions under `*` and `!` patterns exist; whether they reproduce on v2.1 is unknown [U] ([forum 15694](https://forum.syncthing.net/t/trouble-with-recieve-only-folder-unignored-stignore-file-with-and-patterns/15694)).

### Conflict: "nothing downloads until Sync is pressed"

Pausing the folder is not available as a gate, because a paused folder rejects incoming index messages and the file list would stop refreshing [V] ([model.go, handleIndex](https://github.com/syncthing/syncthing/blob/ed2e0fd441cf4ed797f6dee6e3db4d1a6ddb82f5/lib/model/model.go#L1163)). The complete list of folder options contains no pull-hold or index-only flag, and `pullerDelayS` defaults to 1 [V] ([folderconfiguration.go](https://github.com/syncthing/syncthing/blob/ed2e0fd441cf4ed797f6dee6e3db4d1a6ddb82f5/lib/config/folderconfiguration.go#L50)). So download control must come from the whitelist itself: the ignore file holds only what may download right now, the "armed" set, while the user's selection is intent stored by the app [I]. Pressing Sync writes intent into the ignore file; "Download now" adds one file. That resolves the first press. It does not resolve what happens afterwards, because whatever stays whitelisted between sessions is pulled automatically the next time the app is merely open: a new version of an on-device file, and any new file under a directory pattern. Both contradict three statements in `flows.md`: "App visible ... Nothing is downloaded", "the sync network setting limits only the Sync button", and flow 6's "nothing else that is selected is downloaded".

| Option | Effect | Cost | Status |
|---|---|---|---|
| A. Leave the armed set as is | Kept files and selected folders stay current whenever the app is open | Violates the flows and the Wi-Fi-only setting | [I] |
| B. Resting whitelist of per-file lines for files on disk | Stops new files in selected folders; updated versions of on-device files still download | Pattern count equals on-device file count; needs a "no re-hash" check | [I], untested |
| C. Resting whitelist of `*` only | Stops everything | Every on-device row loses its block list, so the next Sync re-hashes every video | [I], rejected |
| D. Small patch that holds the puller | Exact match to the flows | A carried fork of Syncthing, which Sushitrain shows is otherwise avoidable | [I] |
| E. Send-only while browsing | Stops pulls | Makes the phone an authoritative sender; removes the receive-only safety net | [V] basis, rejected |
| F. Folder paused while browsing | Stops pulls | No index refresh | [V], rejected |

The recommendation is option B as the stock-Syncthing baseline, with a product decision on the residue: either reword the flows so that files already on the device refresh while the app is open, or accept option D's patch. This is a decision for the operator, not something research can settle. One lever the notes did not evaluate is a very large `pullerDelayS`; it is worth one prototype check and carries no evidence yet [U].

### What the design must add

**An app-owned tree cache.** Browse has no paging, applies the `levels` filter after scanning every row under the prefix, and reports a directory's own entry size (128 in the docs example), not the sum of its contents [V] ([model.go, GlobalDirectoryTree](https://github.com/syncthing/syncthing/blob/ed2e0fd441cf4ed797f6dee6e3db4d1a6ddb82f5/lib/model/model.go#L2744), [db/browse](https://docs.syncthing.net/rest/db-browse-get.html)). `/rest/db/status` is documented as "an expensive call" [V] ([db/status](https://docs.syncthing.net/rest/db-status-get.html)). Flow 3's "On device" tab across subfolders, sorting by size or date, and per-folder selected-size totals, and flow 2's "opens at once with the last known file list", therefore need a tree the app builds once, refreshes on debounced index events, and persists [I].

**A measured pattern budget.** Matching is a linear loop over all compiled patterns under one mutex, each line compiles to two globs, and every scan matches every local database row; after the first pull pass that is one row per remote file, not per on-device file [V] ([ignore.go, Match](https://github.com/syncthing/syncthing/blob/ed2e0fd441cf4ed797f6dee6e3db4d1a6ddb82f5/lib/ignore/ignore.go#L218), [folder.go](https://github.com/syncthing/syncthing/blob/ed2e0fd441cf4ed797f6dee6e3db4d1a6ddb82f5/lib/model/folder.go#L753)). A 100k-file remote folder with 5k per-file lines is on the order of a billion glob evaluations per full scan [I]. Each `POST /rest/db/ignores` also schedules a full scan [V] ([model.go, setIgnores](https://github.com/syncthing/syncthing/blob/ed2e0fd441cf4ed797f6dee6e3db4d1a6ddb82f5/lib/model/model.go#L2235)). Hence: collapse to directory lines wherever possible, write ignores once per user action rather than per toggle, and measure before freezing option B, whose per-file lines push against this cost [I].

**A strict generator for the ignore file.** Escape `\ * ? [ ] { }` with a backslash, never emit `(?i)` or `#include`, and order exclusions before their parent so that "deselect one child of a selected folder" works through first-match-wins, a case Sushitrain refuses [I]. Lines are trimmed with `strings.TrimSpace`, so names with trailing whitespace or newlines cannot be written literally and need a character-class encoding that is untested [V for the trimming, U for the workaround] ([ignore.go, parseIgnoreFile](https://github.com/syncthing/syncthing/blob/ed2e0fd441cf4ed797f6dee6e3db4d1a6ddb82f5/lib/ignore/ignore.go#L452)). Whether an NFD file name from macOS matches an NFC-normalized pattern on Android was not confirmed [U].

**Explicit handling of partial downloads.** Temp files are named `.syncthing.<name>.tmp` (a SHA-256 form for long names), are re-hashed and reused block by block on resume, and are removed only when a scan walks past them after `keepTemporariesH`, default 24 hours [V] ([tempname.go](https://github.com/syncthing/syncthing/blob/ed2e0fd441cf4ed797f6dee6e3db4d1a6ddb82f5/lib/fs/tempname.go#L19), [walk.go](https://github.com/syncthing/syncthing/blob/ed2e0fd441cf4ed797f6dee6e3db4d1a6ddb82f5/lib/scanner/walk.go#L314), [optionsconfiguration.go](https://github.com/syncthing/syncthing/blob/ed2e0fd441cf4ed797f6dee6e3db4d1a6ddb82f5/lib/config/optionsconfiguration.go#L46)). For an app that runs briefly, a partial can be deleted at the first scan of the next session, just before the pull would have resumed it; raising `keepTemporariesH` to a week or more makes the decision's "partial downloads are kept" true, and the app then owns cleanup on deselect and counts temp files (by allocated size, since they are sparse) in storage figures [I].

**A pairing order rule.** Flow 1 maps onto existing endpoints and events (`/rest/cluster/pending/folders`, `PendingFoldersChanged`, the config endpoints) [V] ([pending folders](https://docs.syncthing.net/rest/cluster-pending-folders-get.html)). The one rule that matters: create the folder paused, write `["*"]`, then unpause, or Syncthing starts downloading the entire folder; `setIgnores` works without a running folder, and Sushitrain uses the same pattern [V] ([model.go](https://github.com/syncthing/syncthing/blob/ed2e0fd441cf4ed797f6dee6e3db4d1a6ddb82f5/lib/model/model.go#L2243), [Sushitrain folder.go](https://github.com/pixelspark/sushitrain/blob/1ed5e2c4728cca8f1673dfb2ae241affa58e7b53/SushitrainCore/src/folder.go#L536)). `autoAcceptFolders` and introducers stay off [I].

Recommended starting folder options, all to validate: watcher off and `rescanIntervalS: 0` with explicit scans (the app is the only writer), `ignorePerms: true`, `ignoreDelete: false`, `maxConflicts: 0`, and `blockIndexing: false` if the database, which scales with the remote folder rather than the selection, turns out large [I]. Two notes disagree on Syncthing's delete-retention default, six months per the v2.0.0 release page and fifteen months per `relnotes/v2.0.md`; both embedders pass 10920 hours explicitly, and Syncbox should do the same and treat the peer's default as unresolved [V for each reading] ([v2.0.0 release](https://github.com/syncthing/syncthing/releases/tag/v2.0.0), [relnotes/v2.0.md](https://github.com/syncthing/syncthing/blob/ed2e0fd441cf4ed797f6dee6e3db4d1a6ddb82f5/relnotes/v2.0.md)).

## One UIDT job per sync, with no foreground service or wake lock

**UIDT fits the manual sync exactly.** A user-initiated job is exempt from standby-bucket quotas, runs in Doze and Battery Saver, and must be scheduled while the app is visible, carry a network constraint, and call `setNotification()` within 10 seconds of `onStartJob()` or the system raises an ANR and stops it [V] ([UIDT guide](https://developer.android.com/develop/background-work/background-tasks/uidt), [JobService.java](https://android.googlesource.com/platform/frameworks/base/+/refs/heads/main/apex/jobscheduler/framework/java/android/app/job/JobService.java), [JobStatus.java](https://android.googlesource.com/platform/frameworks/base/+/refs/heads/main/apex/jobscheduler/service/java/com/android/server/job/controllers/JobStatus.java)). On AOSP `main` the defaults are **6 hours guaranteed, 12 hours per execution, 24 hours cumulative**, dropping to 30 minutes for an app that repeatedly ran into the timeout [V] ([JobSchedulerService.java](https://android.googlesource.com/platform/frameworks/base/+/refs/heads/main/apex/jobscheduler/service/java/com/android/server/job/JobSchedulerService.java)). These constants were read on `main` only, are tunable per device, and were much smaller in older commits; no OEM data on UIDT was found [U]. The alternative, a `dataSync` foreground service, is capped at 6 hours per 24 for apps targeting Android 15+ and needs a Play Console declaration [V] ([FGS timeouts](https://developer.android.com/develop/background-work/services/fgs/timeout), [Play Console Help](https://support.google.com/googleplay/android-developer/answer/13392821)). Google Maps reported a "10%+ improvement in download failure rate" after moving offline downloads to UIDT [V] ([Android Developers Blog](https://android-developers.googleblog.com/2024/09/google-maps-improved-download-reliability-user-initiated-data-transfer-api.html)). WorkManager cannot schedule UIDT ("There is currently no Jetpack library that supports UIDT jobs"), so the app calls `JobScheduler` directly, which minSdk 34 allows without a fallback [V] ([UIDT guide](https://developer.android.com/develop/background-work/background-tasks/uidt)).

**The battery requirement is met by construction.** The system holds the wake lock for a running job, and Play's excessive-wake-lock vital, enforced since March 2026, exempts user-initiated data transfer and tells apps not to take a manual lock for it [V] ([Android Developers Blog, March 2026](https://android-developers.googleblog.com/2026/03/battery-technical-quality-enforcement.html)). The manifest should therefore contain `INTERNET`, `ACCESS_NETWORK_STATE`, `RUN_USER_INITIATED_JOBS`, `POST_NOTIFICATIONS` and `CHANGE_WIFI_MULTICAST_STATE`, and none of `FOREGROUND_SERVICE*`, `WAKE_LOCK`, `RECEIVE_BOOT_COMPLETED` or `REQUEST_IGNORE_BATTERY_OPTIMIZATIONS` [I]. One process-wide engine owner counts holders (UI visible, job running) and stops Syncthing at zero; the process lingering as a cached app afterwards is normal Android behaviour, provided no goroutine keeps timers firing, which must be checked [I]. The vitals risk for this app is ANRs, not battery: the 10-second notification deadline, the roughly 8-second callback timeout, and any engine call on the main thread [V for the timeouts, I for the conclusion] ([JobServiceContext.java](https://android.googlesource.com/platform/frameworks/base/+/refs/heads/main/apex/jobscheduler/service/java/com/android/server/job/JobServiceContext.java)). `onStopJob()` must return within that window while Syncthing shutdown can take longer, so shutdown runs asynchronously and the database must tolerate being frozen or killed mid-shutdown [I]. On Android 16 the `JobParameters` object must be strongly referenced, or the job ends as `STOP_REASON_TIMEOUT_ABANDONED` [V] ([Android 16 behavior changes](https://developer.android.com/about/versions/16/behavior-changes-all)).

**The sync-network setting should be the job's network constraint.** When a constraint is lost the job receives `onStopJob()` and the system retries it later [V] ([UIDT guide](https://developer.android.com/develop/background-work/background-tasks/uidt)); because the system performs the re-run, it should not need the app to be visible, which gives flow 5's "the sync pauses and the notification says why" for free through a detached notification [I, to confirm on API 34 to 37]. "Wi-Fi" then maps to `NET_CAPABILITY_NOT_METERED`, which admits unmetered Ethernet and excludes metered hotspots; the UI text must match whichever meaning is chosen [I]. Not requiring `NET_CAPABILITY_INTERNET` lets a LAN-only sync run on a Wi-Fi without internet [I].

**Pause, Stop and Resume behave as proposed, with one edge the flows omit.** Pause and Stop end the job and stop the engine; Resume as an activity `PendingIntent` that brings the app to the foreground is the guaranteed route [I]. Resuming directly from the notification is probably possible on AOSP, because the system marks every notification `PendingIntent` with background-activity-start allowance and `canScheduleUserInitiatedJobs()` accepts that state, but no documentation promises it [I from V sources] ([NotificationManagerService.java](https://android.googlesource.com/platform/frameworks/base/+/refs/heads/main/services/core/java/com/android/server/notification/NotificationManagerService.java), [ActivityManagerService.java](https://android.googlesource.com/platform/frameworks/base/+/refs/heads/main/services/core/java/com/android/server/am/ActivityManagerService.java)). The Task Manager's Stop kills the process without calling `onStopJob()` and prevents rescheduling, so the app must detect an unfinished sync from persisted state at next launch [V] ([UIDT guide](https://developer.android.com/develop/background-work/background-tasks/uidt)). If the user sets battery usage to Restricted, the job stops as soon as the app leaves the screen; the failure notification should explain that rather than ask for an exemption [V] ([BackgroundJobsController.java](https://android.googlesource.com/platform/frameworks/base/+/refs/heads/main/apex/jobscheduler/service/java/com/android/server/job/controllers/BackgroundJobsController.java)). Flow 7's "the job waits ... until the system ends the job" should change: running into the system timeout counts against the app's timeout quota and can cut later runs to 30 minutes, so the app should end a peerless sync itself after its own timeout [I]. The server-side notification check tests only for a small icon and an existing channel, so a sync with notifications denied should still run, as flow 5 step 1 assumes; this is a prediction from source, not a documented guarantee [I] ([JobNotificationCoordinator.java](https://android.googlesource.com/platform/frameworks/base/+/refs/heads/main/apex/jobscheduler/service/java/com/android/server/job/JobNotificationCoordinator.java)).

**Local-network permission is a dated follow-up, not a first-release item.** With target SDK 36 the app keeps implicit LAN access on Android 14 to 17 and must not declare `ACCESS_LOCAL_NETWORK` [V] ([Local network permission](https://developer.android.com/privacy-and-security/local-network-permission)). When the target moves to 37, the permission becomes a runtime gate on all LAN traffic "deep in the networking stack", including Go's native sockets: TCP times out and UDP fails with `EPERM`, while global discovery and relays keep working [V] (same page). The date of a Play requirement for target 37 comes from secondary sources only [U]. Local discovery additionally needs a `WifiManager.MulticastLock` to receive the computer's announcements on many devices; hold it only while the engine runs [I] ([MulticastLock reference](https://developer.android.com/reference/android/net/wifi/WifiManager.MulticastLock)).

**The later automatic sync is feasible but narrow.** A periodic job constrained to charging and unmetered network gets 10 minutes guaranteed and about 30 at most as a regular job on AOSP `main`, and charging lifts bucket quotas except in the Restricted bucket [V] ([JobSchedulerService.java](https://android.googlesource.com/platform/frameworks/base/+/refs/heads/main/apex/jobscheduler/service/java/com/android/server/job/JobSchedulerService.java), [Power management resource limits](https://developer.android.com/topic/performance/power/power-details)). UIDT "should NOT be used for automatic features" [V] ([JobInfo.Builder](https://developer.android.com/reference/android/app/job/JobInfo.Builder#setUserInitiated(boolean))). The "once every 6 hours" in the requirements is therefore an aim, not a promise: plan each run as resumable, stop voluntarily before 10 minutes, and hand a large backlog to the user with a notification that opens the app and starts a UIDT [I].

## A fake engine and host-side Go tests carry most verification

**The stack is the official default at its smallest.** Compose with Material 3 1.4 stable, Navigation 3 1.2.x (the library the architecture page now names), one screen-level ViewModel per screen exposing a single `StateFlow<UiState>`, no domain layer and no MVI framework [V] ([Architecture recommendations](https://developer.android.com/topic/architecture/recommendations), [Navigation 3 releases](https://developer.android.com/jetpack/androidx/releases/navigation3), [Material 3 releases](https://developer.android.com/jetpack/androidx/releases/compose-material3)). Manual constructor injection with one `AppContainer` is explicitly allowed for simple apps and adds no plugin that breaks on toolchain upgrades [V for the guidance, I for the choice]. OkHttp with kotlinx.serialization covers a dozen localhost endpoints and long-polling; CameraX with zxing-cpp replaces ML Kit, which F-Droid's ban on proprietary Google libraries rules out [V] ([F-Droid Inclusion Policy](https://f-droid.org/en/docs/Inclusion_Policy/), [zxing-cpp Android wrapper](https://github.com/zxing-cpp/zxing-cpp/tree/master/wrappers/android)). zxing-cpp ships a native library, so it falls under the project's 16 KB alignment check; its licence and alignment were not verified [U]. Target SDK 36 makes edge-to-edge and predictive back mandatory and ignores orientation locks on large screens, so every screen is built on `Scaffold` insets from the start [V] ([Android 16, apps targeting API 36](https://developer.android.com/about/versions/16/behavior-changes-16)).

One correction to the architecture note: it recommends DataStore without Room on the premise that "the selection lives in its ignore patterns". The selective-sync findings overturn that premise, since intent must be stored apart from the armed ignore file and the tree needs a persisted cache. Whether that store is a serialized file or Room is open; decide it after measuring a 100k-entry tree [I].

**Toolchain adjustments.** AGP 9.5 requires Gradle 9.6.0 and defaults to NDK 28.2 while the project proposes r30, so `ndkVersion` must be pinned explicitly; AGP 9 has built-in Kotlin and is incompatible with kapt [V] ([AGP release notes](https://developer.android.com/build/releases/gradle-plugin)). Robolectric needs JDK 21 to run tests with SDK 36, so the build toolchain is JDK 21 [V] ([Robolectric releases](https://github.com/robolectric/robolectric/releases)). The gomobile AAR is built from source by a Gradle task with declared inputs and cached by input hash; gomobile's own Gradle plugin lists stale-AAR detection as an open TODO, the repository already rejects committed binaries, and F-Droid wants source builds [V] ([gomobile androidstudio README](https://go.googlesource.com/mobile/+/c909788f9903c3fa409bdba28f909907d69fb3d1/misc/androidstudio/README.md)). Enable R8 from the first build and smoke-test the minified APK, because gomobile-generated classes need keep rules [U].

**The module boundary is what makes agents effective.** A pure-Kotlin `SyncEngine` interface with domain models and the selection-to-pattern logic sits between the app and Syncthing; it is implemented once for real (gomobile plus REST) and once as an in-memory fake with a 100k-entry generator [I]. This follows Google's "Prefer fakes to mocks" and Now in Android's interface-first data layer [V] ([Architecture recommendations](https://developer.android.com/topic/architecture/recommendations), [nowinandroid](https://github.com/android/nowinandroid)). A shared contract test suite run against both implementations keeps the fake honest, and the interface also hides the in-process versus separate-process question until restart tests answer it [I].

| Level | What it checks | Where | Tooling |
|---|---|---|---|
| 0 | Lint as errors, formatter, dependency verification, licence allow-list, banned-dependency rule, 16 KB alignment | Host | Gradle and pinned tools |
| 1 | Device-ID validation, selection to ignore patterns, REST parsing, ViewModels on the fake engine | JVM | JUnit, coroutines-test, MockWebServer |
| 2 | Compose screens: semantics, navigation, dialogs, denied-permission paths | JVM | Robolectric |
| 3 | Screenshots of every screen and state | JVM | Roborazzi, goldens recorded on Linux |
| 4 | Real Syncthing bridge against a second Syncthing | Host, no emulator | Go tests on `linux/amd64` |
| 5 | UIDT job, notification actions, `FileProvider` grants, library load, R8 smoke | Emulator | AndroidX Test, UI Automator |
| 6 | Pair, accept, select, Sync, leave app, finish, open in VLC | Emulator plus host peer | Script plus instrumented tests |
| 7 | Exploratory look after UI work | Emulator | adb or Android CLI |

The table is a proposal [I]; its tooling choices rest on sources. Roborazzi is actively released and is what Now in Android uses, whereas Google's standalone screenshot plugin "is no longer maintained" and its AGP replacement is experimental [V] ([Roborazzi releases](https://github.com/takahirom/roborazzi/releases), [Compose Preview Screenshot Testing](https://developer.android.com/studio/preview/compose-screenshot-testing)). Recorded screenshots double as the agent's eyes at a fraction of an emulator's cost [I]. **Level 4 is the unusual, highest-value layer**: receive-only plus whitelist behaviour, deselect ordering, pause and stop, partial files and restart loops need no Android at all [I]. For level 6, the emulator sits behind NAT and reaches the host at `10.0.2.2`, so the phone dials a hermetic host Syncthing at a static `tcp://10.0.2.2:<port>` address with discovery and relays off on both sides; this requires a debug-only hook, since production has no such setting, and a test asserting that the hook is absent from release builds [I] ([emulator networking](https://developer.android.com/studio/run/emulator-networking-address), [Syncthing config docs](https://docs.syncthing.net/users/config.html)). No report of anyone testing Syncthing on an emulator against a host peer was found, so the wiring is derived, not proven [U]. ATD images are unsuitable because they strip SystemUI and the docs still list them at API 30 [V] ([Gradle Managed Devices](https://developer.android.com/studio/test/gradle-managed-devices)). Whether the yard's emulator has KVM decides if levels 5 and 6 run locally or only in CI; recording that is the first step of the `verification-setup` task [I].

Agent-facing practice follows from this: one script per level under `dev/`, each printing every failure, with CI calling the same scripts; all tools pinned by version and checksum; constraints such as the Play Services ban, licence allow-list and 16 KB alignment expressed as failing checks instead of prose; flow numbers in test names plus a traceability table mapping each flow and each "still has to be verified" decision to the test that covers it; and a demo run mode on the fake engine so UI work never waits for Syncthing [I]. Evidence for agent-specific practices is thin, mostly vendor posts and practitioner write-ups read only as search digests [U]. Google's Android CLI gives agents device control and preview rendering without Android Studio, but its headless behaviour in a Linux container was not confirmed, and it collects telemetry unless `--no-metrics` is set [V for the features, U for headless use] ([Android CLI overview](https://developer.android.com/tools/agents/android-cli)).

## Internal storage holds; the VLC hand-off is the unproven requirement

**The storage decision is sound for a receive-only copy.** Internal app storage needs no permission, is encrypted, and is not FUSE-mounted [V] ([App-specific storage](https://developer.android.com/training/data-storage/app-specific), [AOSP scoped storage](https://source.android.com/docs/core/storage/scoped)). All-files access is not a route for this product: Play's permitted uses do not name file sync and list "Media Files access" as not permitted [V] ([Play Console help](https://support.google.com/googleplay/android-developer/answer/10467955)). The costs belong in the decision record: no gallery, USB or SD-card access; everything is deleted on uninstall and on "Clear storage"; external players receive a URI and never a path [I]. Because the phone holds a disposable copy of data that lives on the computer, deletion loses only download time, and that argument would not hold for a send or bidirectional folder [I]. The free-space gate in flow 5 should use `StorageManager.getAllocatableBytes()` and count temp files [V for the API] ([App-specific storage](https://developer.android.com/training/data-storage/app-specific)).

**Backup rules are a missing requirement.** Auto Backup includes `getFilesDir()` by default, a missing `<device-transfer>` section enables device-to-device transfer of everything, and cloud backup stops entirely above 25 MB [V] ([Auto Backup](https://developer.android.com/identity/data/autobackup)). Syncthing's device ID derives from `cert.pem` and `key.pem`, and two devices running one pair appear as a single device and fail to connect properly [V] ([forum: equal IDs](https://forum.syncthing.net/t/equal-ids-on-different-computers/10999)). A restore or phone-to-phone transfer would create exactly that state. Keep synced files, the Syncthing database, config and keys under `getNoBackupFilesDir()` or exclude them from every transfer mode, and let a new install pair again; only user preferences are safe to back up [I].

**"VLC must work" is plausible from source and unproven on a device.** `FileProvider` with `ACTION_VIEW`, an explicit MIME type and `FLAG_GRANT_READ_URI_PERMISSION` is the documented path, and `startActivity` with a caught `ActivityNotFoundException` needs no `<queries>` entry for flow 8's "no app can open it" case [V] ([FileProvider reference](https://developer.android.com/reference/androidx/core/content/FileProvider), [Package visibility use cases](https://developer.android.com/training/package-visibility/use-cases)). VLC's code looks up a MediaStore `DATA` column, and if that yields no readable file for a `content` URI it opens a file descriptor from the provider and plays an `fd://` location; mpv-android opens the descriptor and falls back to the content URI [V, read through a summariser, exact control flow to confirm] ([FileUtils.kt](https://raw.githubusercontent.com/videolan/vlc-android/master/application/vlc-android/src/org/videolan/vlc/util/FileUtils.kt), [MPVActivity.kt](https://raw.githubusercontent.com/mpv-android/mpv-android/master/app/src/main/java/is/xyz/mpv/MPVActivity.kt)). The descriptor points at a regular file, so seeking in multi-gigabyte files should work [I]. Tickets titled "VLC for Android cannot open URIs from FileProvider" exist, and their state could not be read [U] ([vlc-android 1817](https://code.videolan.org/videolan/vlc-android/-/issues/1817)). Whether VLC 3.7.x opens, seeks and titles a stock `FileProvider` URI is the single most important device check for the first release.

The intent should carry more than the flows specify: an explicit MIME type from the app's own extension table, because the platform map is unreliable for containers such as `.mkv` or `.ts` and mpv requires `video/*` [I]; a `title` extra, or VLC may display an `fd://` location [I]; a start position; and `ClipData` so one grant covers sibling subtitle URIs [V for the `ClipData` rule] ([FileProvider reference](https://developer.android.com/reference/androidx/core/content/FileProvider)). Resume position should be stored by Syncbox from the player's result intent, since a grant lasts only while the receiving task is alive and VLC does not persist content URIs across state restore [V for both facts, I for the design] ([VideoPlayerActivity.kt](https://raw.githubusercontent.com/videolan/vlc-android/master/application/vlc-android/src/org/videolan/vlc/gui/video/VideoPlayerActivity.kt)).

**External subtitles are the known casualty.** A player given one URI cannot find sibling files. mpv-style `subs` extras take URIs and are well defined [V] ([mpv-android intent documentation](https://mpv-android.github.io/mpv-android/intent.html)). VLC reads `subtitles_location` as a plain string, and an issue reports that it does not accept content URIs; its state is unknown [U] ([vlc-android 2314](https://code.videolan.org/videolan/vlc-android/-/issues/2314)). If the device test fails, external subtitles in VLC are a documented first-release limitation, as are multi-file formats. A `DocumentsProvider` in the style of Termux's would add file-manager access and export later but does not fix sibling subtitles [I] ([TermuxDocumentsProvider.java](https://raw.githubusercontent.com/termux/termux-app/master/app/src/main/java/com/termux/filepicker/TermuxDocumentsProvider.java)).

**The built-in player should start from Media3.** Media3 is at stable 1.11.1 with active Matroska, AVI and MPEG-TS work, but its ASS/SSA rendering is limited, which Findroid and Next Player both state for their ExoPlayer paths [V] ([Media3 release notes](https://developer.android.com/jetpack/androidx/releases/media3), [Findroid README](https://raw.githubusercontent.com/jarnedemeulemeester/findroid/main/README.md), [Next Player README](https://raw.githubusercontent.com/anilbeesetti/nextplayer/main/README.md)). libVLC ships a single AAR (3.7.7 on Maven Central) with a 16 KB fix backported to 3.x, while its 4.0 line is still early access; mpv-android states it is not an importable library [V] ([Maven Central](https://repo1.maven.org/maven2/org/videolan/android/libvlc-all/), [libvlcjni MR 140](https://code.videolan.org/videolan/libvlcjni/-/merge_requests/140), [mpv-android README](https://raw.githubusercontent.com/mpv-android/mpv-android/master/README.md)). The recommendation is Media3 with an FFmpeg audio extension, keeping "Open in external player" permanently for what it cannot handle; a built-in player reads paths directly, which is what restores sibling subtitles and resume [I]. Size and licence figures for the alternatives are unsourced estimates and must be measured before the choice is final [U]. Playing a file while it downloads is out of reach with external players, and the notes' explanation (sparse temp files filled out of order) is itself unsourced [U]. Thumbnails can wait: the first release shows type icons, and Coil's video module works on local paths when wanted [V] ([Coil video frames](https://coil-kt.github.io/coil/videos/)).

Three passages of `flows.md` conflict with findings and need rewording once the product decision is made. The first is the Sync-button group already described: "Nothing is downloaded" while visible, the sync-network setting limiting "only the Sync button", and flow 6's "nothing else that is selected is downloaded". The second is "App leaves the screen with no sync running: Syncthing stops": a session too short for the pull pass to process ignored files leaves the phone looking out of sync on the computer until its next session, and self-healing of any transient state never runs [I]. The third is flow 7's wait "until the system ends the job", which trades a clean failure for a timeout penalty. The flows also lack states that Syncthing will produce regardless: a selected file deleted on the computer is deleted on the phone by a normal pull, and a remote rename is a removal plus a creation, so a per-file selection is silently lost while a folder-level selection survives [V for the rename pitfall, I for the deletion] ([Sushitrain README](https://github.com/pixelspark/sushitrain/blob/1ed5e2c4728cca8f1673dfb2ae241affa58e7b53/README.md)). Finally, "accept the folder" in flow 1 needs the paused-create rule, and flow 4's "deleted at once" needs the scan wait behind it.

## Conclusion

The research moves the project's risk from "can this be built" to two narrower places. Syncthing embedding, the whitelist, receive-only safety, UIDT and internal storage each have production precedent or primary-source support; what has no precedent is Syncbox's specific shape, an engine that starts and stops many times a day and a whitelist that must stay quiet until a button is pressed. Sushitrain solves neither, since it runs one engine per process and downloads whatever is selected. Those two questions, not the UI or the Android job plumbing, determine whether upstream Syncthing can be used unpatched, and both can be answered in days by Go tests on a desktop.

That is also the practical argument for relaxing "no prototypes yet". The rule exists so that an agent can build and fully check a prototype on its own; the engine harness is the part of the verification setup that makes this true, and it produces the facts the design is waiting for. Treating it as verification infrastructure, with the Kotlin interface and the fake engine following immediately, keeps the original intent and removes the one circular dependency in the plan: the design cannot be approved until behaviour is known, and behaviour cannot be known without running Syncthing.
